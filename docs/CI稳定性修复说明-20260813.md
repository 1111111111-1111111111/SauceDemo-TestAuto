# SauceDemo 自动化测试 — CI 稳定性修复说明（2026-08-13）

> 针对 GitHub Actions（Linux 容器环境）下测试偶发 ERROR/FAILED、构建告警的三项修复。
> 涉及 9 个文件，全部已通过语法/YAML 校验。

---

## 一、pytest-rerunfailures 重试配置

**背景**：CI 访问外部站点 saucedemo.com 存在偶发网络抖动，测试在 setup/call 阶段可能随机失败。

| 文件 | 修改 |
|:--|:--|
| `pytest.ini` | `addopts` 追加 `--reruns 2 --reruns-delay 3` |
| `requirements.txt` | `pytest-rerunfailures==13.0` → `==16.4` |

**为什么升级 16.4**：原 13.0（2023-11 发布）仅支持 pytest ≤ 8.1，项目使用 **pytest 9.1.1**；16.4（2026-07-01 发布）正式支持 pytest 9.x。升级后：
- 每条失败用例最多重跑 2 次，间隔 3 秒
- **setup 阶段失败（如 fixture 里的 go_to_cart）也会重跑**——正好覆盖之前 `test_cart_checkout_to_step_one` 的 ERROR 场景
- 重试成功后用例判 PASS，Allure 报告仍保留失败历史

## 二、Linux CI 视角的 find_element 卡顿隐患全量排查（6 个文件）

### 排查结论：Windows 正常 / Linux 失败的根因

Windows 本地机器性能好、网络延迟低，元素"碰巧"在超时前出现；Linux 容器（GitHub Actions runner）首次启动 Chrome 慢、到外部站点延迟高，同一段代码的时序差异被放大，暴露出两类隐患：

| 隐患类型 | 现象 | 根因 |
|:--|:--|:--|
| **A. 空状态等满超时** | 购物车为空/badge 消失时，`find_element`/`get_text` 等满 EXPLICIT_WAIT=10s + 生成 element_not_found 截图 | 空状态是**合法业务状态**，但代码用了"等待元素出现"的语义 |
| **B. 页面未渲染完即查** | 直接 `driver.find_element`（隐式等待=0），页面加载慢时立即抛 NoSuchElementException → flaky | 应使用显式等待 |

### 修复明细

| 文件 | 方法 | 修复 |
|:--|:--|:--|
| `pages/base_page.py` | `find_elements()` | 新增 `timeout` 参数（默认 EXPLICIT_WAIT）；空集合超时返回 `[]`，**不抛异常、不截图**，日志降级为 warning |
| `pages/products_page.py` | `get_cart_badge_count()` | 改为 `find_elements(..., timeout=1)` 快速判断，空购物车零等待 |
| `pages/product_detail_page.py` | `open_cart()` | 与 `go_to_cart()` 同款方案：**优先读 `<a>` 的 href 用 `driver.get()` 直连导航**，绕开 React 事件未绑定窗口期，再等 URL + `#checkout` 关键元素双保险 |
| `pages/product_detail_page.py` | `get_cart_badge_count()` | 同上改短超时快速判断 |
| `pages/checkout_complete_page.py` | `get_cart_badge_count()` / `is_cart_reset()` | 完成结账后 badge 消失是**必然事件**，原代码每次都等满 10s + 截图（CI 上 element_not_found_badge 截图来源之一）；改为 `find_elements(..., timeout=1)` |
| `pages/cart_page.py` | `get_item_count()` | 改为 `find_elements(..., timeout=2)`：`remove_all_items()` 清空购物车后末次轮询不用白等 10s（`test_cart_remove_all_items` 原需等 2×10s，修复后 ≈0） |
| `pages/login_page.py` | `get_password_input_type()` 等 3 个方法 | `driver.find_element` → `self.find_element()` 显式等待，防 CI 页面未渲染完立即抛错 |
| `pages/login_page.py` | `is_error_displayed()` | 改为 `bool(self.find_elements(..., timeout=1))`，快速判断且不依赖隐式等待配置 |

### 收益估算

- `test_cart_remove_all_items`：20s+ → 秒级
- 所有 badge 检查（3 处）：每次调用 10s+截图 → 0s
- 登录页属性读取（3 处）：从"可能立即抛错"→ 最多等 10s 直到元素出现

## 三、Node 20 弃用警告修复（ci.yml，9 处）

### 重要澄清：警告与 Dockerfile 无关

GitHub 从 2025-09 起弃用 Node 20 运行器，2026 年起 runner 默认用 Node 24。**警告来自 GitHub Actions 中 action 的运行环境**（`docker/setup-buildx-action@v3` 等 action 内部声明 `runs.using: node20`），**不是 Dockerfile**——本项目 Dockerfile 基于 `python:3.12-slim`，镜像内**没有 Node.js**，也无需 Node（Selenium + pytest + Allure 均不需要）。因此正确修复是升级 workflow 中的 action 版本，而非修改 Dockerfile。

### 升级明细（全部为默认运行 Node 24 的版本）

| Action | 原版本 | 新版本 | 说明 |
|:--|:--|:--|:--|
| `actions/checkout` | v4 | **v6** | 3 处 |
| `docker/setup-buildx-action` | v3 | **v4** | 警告的直接来源 |
| `docker/login-action` | v3 | **v4** | |
| `docker/build-push-action` | v5 | **v7** | |
| `actions/upload-artifact` | v4 | **v7** | 2 处；v6 起默认 Node 24 |
| `actions/download-artifact` | v4 | **v8** | v7 起默认 Node 24 |
| `peaceiris/actions-gh-pages` | v4 | **保持 v4** | Pages 部署 action，非 Node 运行时 |

已通过 YAML 解析校验，workflow 四个 job（build-and-push / test / deploy-pages / notify）结构完好。

